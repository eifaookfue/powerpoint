パスパラメータとクエリパラメータはどのように使い分ければいいですか？

**パスパラメータ**（Path Parameters）と**クエリパラメータ**（Query Parameters）は、REST APIでリクエストデータを渡すための2つの方法です。それぞれの使い分けには明確なルールや推奨があります。以下にその違いと使い分けの基準を説明します。

---

### **1. パスパラメータ（Path Parameters）**

#### **概要**
- URLパスの一部として指定されるパラメータ。
- 特定のリソースを識別するために使用される。

#### **使い方**
- **リソースの識別子（IDや名前）を渡す場合**に使用。
- パス内で動的に変わる部分を表現。

#### **例**
```plaintext
GET /users/{userId}/orders/{orderId}
```
**解釈**:
- `userId`: ユーザーを特定するための識別子。
- `orderId`: 特定の注文を指定。

---

### **2. クエリパラメータ（Query Parameters）**

#### **概要**
- URLの末尾に`?`で始まるキーと値のペア（`key=value`）として指定。
- リクエストの追加情報（フィルタリング、ソート、ページングなど）を指定するために使用。

#### **使い方**
- **リソースの取得条件や操作のカスタマイズ**を指定する場合に使用。
- パス全体に対して適用されるオプション的な情報を表現。

#### **例**
```plaintext
GET /users?role=admin&status=active&page=1
```
**解釈**:
- `role=admin`: 管理者ロールを持つユーザーをフィルタリング。
- `status=active`: 有効なユーザーのみを取得。
- `page=1`: ページネーション。

---

### **3. パスパラメータとクエリパラメータの使い分け**

#### **使い分けの基準**
| **用途**                           | **パスパラメータ**                | **クエリパラメータ**              |
|-----------------------------------|----------------------------------|----------------------------------|
| **特定のリソースの識別**             | 使用する（リソースIDなど）          | 使用しない                       |
| **リソースのフィルタリングやカスタマイズ** | 使用しない                        | 使用する（オプション情報）         |
| **RESTfulな設計の一貫性**             | リソース名/識別子として適切         | 条件や制限として適切              |
| **値が必須かどうか**                 | 必須                              | 任意（指定しない場合も意味を持つ） |

---

#### **具体例: ユーザー情報の取得**

1. **特定のユーザーを取得**  
   - パスパラメータを使用。リソースそのものを特定する。
   ```plaintext
   GET /users/{userId}
   ```

2. **ユーザーの条件付き検索**  
   - クエリパラメータを使用。取得条件を指定。
   ```plaintext
   GET /users?role=admin&status=active
   ```

3. **特定ユーザーの注文情報を取得**
   - パスパラメータでリソースを特定し、クエリパラメータで条件を指定する。
   ```plaintext
   GET /users/{userId}/orders?status=shipped&sort=desc
   ```

---

### **4. ベストプラクティス**
1. **リソースの識別はパスパラメータを使用**:
   - パスパラメータはURLの構造を表現し、リソースを特定するために使用。
   - 例: `/users/{userId}` はRESTfulなエンドポイント設計に合致。

2. **フィルタリングや検索条件はクエリパラメータを使用**:
   - クエリパラメータは、リソースに対する追加情報や条件を指定するために使用。
   - 例: `/users?role=admin` はロールでのフィルタリング。

3. **意味のある構造を持たせる**:
   - パスパラメータで「何を取得するか」を明示し、クエリパラメータで「どう取得するか」を指定する。

4. **値の必須性を意識**:
   - パスパラメータは通常必須。
   - クエリパラメータはオプション情報を指定するため、任意の場合が多い。

---

### **5. 注意点**
- **パスの可読性**:
  - パスパラメータで過剰に情報を詰め込むとURLが不必要に複雑になります。

- **クエリパラメータの制限**:
  - クエリパラメータはブラウザやサーバーによって長さに制限があるため、大量のデータには不向き。

- **RESTfulな設計の一貫性**:
  - 設計段階でパスパラメータとクエリパラメータの用途を明確に分け、統一性を保つことが重要です。

---

### **まとめ**
- **パスパラメータ**は「どのリソースか」を指定する際に使用。  
  例: `/users/{userId}`  
- **クエリパラメータ**は「リソースをどう取得するか」を指定する際に使用。  
  例: `/users?role=admin&status=active`  
- RESTful APIの一貫性を保つため、この基準を守ることで開発と利用が効率的になります。
